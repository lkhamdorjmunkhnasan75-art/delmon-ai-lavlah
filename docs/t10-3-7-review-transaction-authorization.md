# T10.3.7 reviewer transaction authorization

Migration 019 requires READ COMMITTED for the atomic review entry point. The existing permission and organization advisory locks order competing reviews, including reviews of different permissions for the same organization. READ COMMITTED allows the function to see publications committed while it was waiting. The binding lookup takes a row-level SHARE lock for the original database login. The review also retains the existing SHARE locks on the source permission and reviewer grant.

A committed binding deletion or reassignment prevents further use of that binding. If revocation holds the row first, a waiting review reevaluates the row after the administrator commits. If review holds the row first, the administrator waits until that transaction finishes. Permission and grant updates and deletes obey the same lock ordering principle. PostgreSQL can abort deadlocks when transactions lock multiple resources in differing orders. Retry the whole transaction in a fresh session if retrying is appropriate. The application keeps its existing bounded review statement timeout.

An initially deferred constraint trigger rechecks login binding, role membership, source permission and reviewer grant for approvals and rejections. Approvals also check the stored source expiry against the database wall clock. Under the normal application path the trigger runs during commit processing. Failure rolls back the review, publication, source and audit together. Trusted administrative writes and historical imports do not queue this trigger. Migration 019 down restores the 018 wrapper and drops the trigger without rewriting existing rows.

## Residual limits

- The deferred trigger runs before PostgreSQL finishes COMMIT. Catalog role changes such as REVOKE or NOLOGIN do not share the binding row lock. There is a residual window after the last check and before durable commit. Use a committed binding deletion as the primary revocation operation. For urgent cutoffs, coordinate disabling the login and terminating its existing backends.
- A client with direct reviewer SQL access controls its transaction and can make deferrable checks run early using SET CONSTRAINTS. PREPARE TRANSACTION also runs deferred checks before COMMIT PREPARED when two-phase commit is enabled. Keep prepared transactions disabled for this deployment and keep reviewer SQL credentials confined to the review worker, whose strict path commits immediately after returning from its final database check. A long-running reviewer transaction can delay revocation. Validate server-side session and idle transaction limits in staging.
- The login binding limits database identity. The application identity token and its expiry remain separate from the review database transaction. Existing directory snapshots can keep earlier visibility. Previously committed publication is governed by the public directory's source permission and freshness rules.
- Trusted maintenance roles can modify data or DDL outside the atomic entry point. Coordinate maintenance of candidates, grants, permissions and listings with review traffic. Dedicated credential provisioning, earlier definer ownership and independent review remain open. A01, A02, A05 and A12 remain open. Production remains NO-GO.

The PostgreSQL workflow applies, rolls back and reapplies migration 019 before running the synthetic pilot tests with separate database connections.
